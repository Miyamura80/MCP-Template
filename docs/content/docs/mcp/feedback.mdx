title: Feedback
description: Where agent feedback goes - the database, Slack and Linear
---

Agents call the `feedback` tool when they get stuck: a tool errors in a way they
cannot recover from, a description misled them, or a capability is missing.
Every submission is written to the `agent_feedback` table first, then offered
to each configured sink. A sink that is down or misconfigured is logged and
skipped; it never fails the agent's call, and the tool result's
`forwarded_to` lists the sinks that accepted it.

```
feedback(...) --> agent_feedback table (always)
              --> Slack   (if FEEDBACK_SLACK_WEBHOOK_URL)
              --> Linear  (if FEEDBACK_LINEAR_API_KEY + feedback.linear.team_id)
              --> your own registered sinks
```

Sinks run inline, after the row is stored, so the result can say where the
feedback went. Each sink gets a total budget of `feedback.sink_timeout_seconds`
(default 3) per submission, so a slow sink delays the call by about that much
at most.

## Slack

Create an [incoming webhook](https://api.slack.com/messaging/webhooks) and set
it in `.env`:

```bash
FEEDBACK_SLACK_WEBHOOK_URL=https://hooks.slack.com/services/...
```

## Linear

Put the personal API key (Linear: Settings > Security & access) in `.env`:

```bash
FEEDBACK_LINEAR_API_KEY=lin_api_...
```

and the team in `common/global_config.yaml`. The sink is off unless both the
key and `team_id` are set:

```yaml
feedback:
  linear:
    team_id: "<team uuid>"            # required: the team that owns the issues
    label_ids: ["<label uuid>"]       # optional: applied to new issues
    project_id: "<project uuid>"      # optional: new issues go in this project
```

The key acts as the user who created it, so a dedicated bot user keeps the
issues from appearing under a person's name.

### One issue per problem

A problem is identified by its `category` plus `tool_name`. The sink writes a
fingerprint token (`agent-feedback-<16 hex>`) as the last line of the issue
description. On each submission it looks in the team for an issue whose
description ends with that token and whose state is not completed, canceled or
duplicate:

- **Found:** the report is added to that issue as a comment.
- **Not found:** a new issue titled `[agent-feedback] <category> on <tool>` is
  created.

So closing an issue means the next report of the same problem opens a fresh
one. Retitling an issue is fine; removing the fingerprint line from its
description stops new reports from finding it. Two reports that arrive at the
same moment can, rarely, both create an issue.

Agent-written text is untrusted: the message and context are placed in code
blocks with backticks neutralised, so they cannot add mentions, links or
formatting, and any `agent-feedback-` they contain is altered so an agent
cannot plant another problem's token and redirect its reports. The original
text is kept unchanged in the database.

## Your own sink

Implement `FeedbackSink` (a `name` and a `send(record)` that raises on failure)
and register it at import time with `register_feedback_sink()` from
`services/feedback_svc.py`. Registering a sink named `slack` or `linear`
replaces the built-in one.

```python
from services.feedback_sinks import FeedbackRecord, SinkClient, SinkError
from services.feedback_svc import register_feedback_sink


class JiraSink:
    name = "jira"

    def send(self, record: FeedbackRecord) -> None:
        with SinkClient() as client:  # one HTTP client + the time budget
            body = client.post_json(JIRA_URL, {...}, headers={"Authorization": KEY})
        if not body:
            raise SinkError("Jira returned nothing")


register_feedback_sink(JiraSink())
```

`SinkClient.post_json` returns the parsed JSON body and raises `SinkError` on a
transport error, a non-2xx status or a spent budget, with a message that never
includes the URL or headers. Failures are logged as the exception type and
message only, without a traceback (whose frame locals could hold your
secrets), so keep your own exception messages free of secrets too.
