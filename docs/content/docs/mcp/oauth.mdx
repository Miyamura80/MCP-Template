## Overview

The `/mcp` endpoint supports the MCP authorization spec (2026-07-28): this
server acts as an OAuth 2.1 **resource server**, and [WorkOS
AuthKit](https://workos.com/docs/authkit/mcp) acts as the **authorization
server**. AuthKit handles client registration (Client ID Metadata Documents
and Dynamic Client Registration), PKCE, and user consent, then issues access
tokens audience-bound to this server. Clients like Claude (web and Desktop)
connect with zero manual provisioning: no client IDs, no pasted keys.

API keys (`X-API-KEY`) and WorkOS session JWTs keep working as parallel auth
paths for machine and internal clients.

## What the server implements

- **Protected Resource Metadata (RFC 9728)** at
  `/.well-known/oauth-protected-resource/mcp` (path form, tried first by
  clients) and `/.well-known/oauth-protected-resource`. It names the canonical
  resource URI and points at your AuthKit instance.
- **Authorization Server Metadata (RFC 8414)** at
  `/.well-known/oauth-authorization-server` (and the `/mcp` path form). AuthKit
  is the authorization server and publishes its own RFC 8414 document; the
  spec-correct discovery path is PRM → AuthKit. But many MCP clients and
  registry crawlers probe this well-known against the *resource server* origin
  directly, so the server redirects (`307`) those requests to AuthKit's
  authoritative metadata. Both endpoints return `404` when OAuth is unconfigured.
- **Discovery hint on 401**: unauthenticated `/mcp` requests get
  `WWW-Authenticate: Bearer realm="mcp", resource_metadata="..."`, which is
  how clients bootstrap the flow.
- **Audience-bound token validation (RFC 8707)**: AuthKit access tokens are
  verified against the AuthKit JWKS, with the issuer pinned to your AuthKit
  domain and the audience pinned to `MCP_PUBLIC_URL`. Tokens minted for any
  other resource are rejected. The token's `sub` becomes the `user_id` seen by
  tools (same `current_user()` plumbing as the other auth methods), and a
  `scope` claim maps onto the server's scope checks.

## Setup

1. In the WorkOS dashboard, enable AuthKit and go to **Connect →
   Configuration**. Enable **Client ID Metadata Documents** (and optionally
   **Dynamic Client Registration** for older clients), and register your MCP
   server's public URL as a **resource indicator**, e.g.
   `https://your-deployment.example.com/mcp`.
2. Set the two environment variables in `.env`:

```bash
WORKOS_AUTHKIT_DOMAIN=https://your-env.authkit.app
MCP_PUBLIC_URL=https://your-deployment.example.com/mcp
```

`MCP_PUBLIC_URL` must match the resource indicator exactly (no trailing
slash); tokens are audience-bound to this string, so a mismatch yields silent
401s.

3. Restart `mymcp-serve`. Verify discovery:

```bash
curl https://your-deployment.example.com/.well-known/oauth-protected-resource/mcp
```

```json
{
  "resource": "https://your-deployment.example.com/mcp",
  "authorization_servers": ["https://your-env.authkit.app"],
  "bearer_methods_supported": ["header"]
}
```

4. Add the server to an MCP client by URL alone (no headers). The client
   discovers AuthKit, registers itself, and opens the consent screen.

## Built-in authorization server (opt-in)

Tokens that AuthKit issues for MCP have no revocation endpoint, so signing a
user out cannot end the sessions their apps hold. Set `MCP_AUTH_MODE=self` and
this server becomes the authorization server itself: it issues, stores and
revokes the tokens, and AuthKit only signs the user in. The default is
`authkit`; setting it back is the rollback.

```
MCP client ──/authorize──► this server ──consent page──► AuthKit sign-in
     ▲                                                       │
     └──── code + iss ◄── /oauth/workos/callback ◄───────────┘
     ──/token (PKCE)──► opaque, hashed, revocable tokens ──► /mcp
```

What it does (`api_server/oauth/`):

- **Client ID Metadata Documents** only; Dynamic Client Registration is
  deprecated in the 2026-07-28 spec and is refused. The document fetch goes
  through an SSRF guard (`services/_ssrf_guard.py`) with a 5 s deadline, a
  10 KB cap and a short cache. Only public clients
  (`token_endpoint_auth_method: none`) are accepted.
- A **consent page** names the client and the redirect host (with a warning
  for loopback redirects) before the user is sent to AuthKit, and binds each
  sign-in to its browser with a cookie nonce.
- **PKCE S256** only, exact redirect matching (any port on loopback, RFC 8252),
  `iss` on every authorization response (RFC 9207), tokens bound to
  `MCP_PUBLIC_URL` (RFC 8707).
- Codes and tokens are random and stored only as SHA-256 hashes (migration
  `015`). Access tokens live one hour; refresh tokens rotate, a reused one
  revokes its whole grant, and a grant ends 90 days after sign-in.
- `/revoke` follows RFC 7009 for public clients.
- `api_server.oauth.storage.revoke_user_grants(user_id)` revokes every token a
  user holds and refuses any sign-in already under way. Call it from your own
  sign-out (for example a `mutating=True` service); the template does not ship
  one.

Setup:

```bash
MCP_AUTH_MODE=self
MCP_PUBLIC_URL=https://your-deployment.example.com/mcp
WORKOS_CLIENT_ID=client_...
WORKOS_API_KEY=sk_...
SESSION_SECRET_KEY=<a long random value>
```

Add `https://your-deployment.example.com/oauth/workos/callback` as a redirect
URI in the WorkOS dashboard. Outside development the server refuses to start in
this mode without a real `SESSION_SECRET_KEY` and `MCP_PUBLIC_URL`. Run
`make db_migrate` for the token tables. The protected-resource and
authorization-server metadata then point at this origin, and `/mcp` accepts only
tokens this server issued (plus `X-API-KEY`).

## Conformance testing

[MCPJam](https://github.com/MCPJam/inspector) ships an OAuth conformance
suite. It drives a real browser consent flow, so it is a manual check rather
than part of CI:

```bash
npx -y @mcpjam/cli@latest oauth conformance \
  --url https://your-deployment.example.com/mcp \
  --protocol-version 2025-11-25 \
  --conformance-checks
```

Protocol and apps conformance run in CI against the API-key path (see
`make mcp_conformance`).
